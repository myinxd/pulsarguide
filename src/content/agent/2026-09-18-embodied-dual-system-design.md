> 一个 VLM 做一次前向推理，几十到几百毫秒。一只人形机器人的手要稳稳抓住一个杯子，控制回路得跑在每秒 100 到 200 次。
> 这两个数字放在一起只有一个结果：**负责思考的那个模型，来不及管动作。**
> 所以现在几乎所有前沿的具身大脑，都在同一个地方做了同一个妥协——分层。

上一篇[讲路线收敛](/agent/posts/2026-09-18-embodied-vla-world-model-wam/)时留了个尾巴：**双系统的理由不是「大脑不够强」，是频率不匹配。** 这篇把它展开。

## 一、先看这道题有多硬

拆解一下数字。一个 7B 参数的 VLM，在机器人本体的 GPU 上跑一次推理，7–9 Hz 是当前的现实水平。也就是说它每 110 到 140 毫秒才能更新一次「我对世界的理解」。

而机器人的控制回路需要 100–200 Hz。抓握的力反馈、手腕的微调、平衡的补偿，都在这个尺度上发生。

**差了 20 到 30 倍。** 这不是优化能填平的量级差距，因为瓶颈在模型规模本身——你想让语义理解更强，就得用更大的模型，延迟只会更高。

于是分层成了唯一的工程解：

```
S2（慢而聪明）  VLM，7–9 Hz   →  理解场景、理解指令、决定做什么
                              ↓ 传递一个压缩后的表征
S1（快而精准）  策略网络，100–200 Hz  →  把它变成关节角度
```

这里有个关键设计值得停一下：**S2 传给 S1 的不是文字，是一个连续潜在向量。** 用自然语言做接口听起来更优雅，但会引入离散化的信息损耗和额外延迟。现在主流做法都是让 S2 把任务相关信息蒸馏成一个向量，投影进 S1 的 token 空间，和视觉特征拼在一起做条件。

下面看三家怎么答这道题。

## 二、Helix：把分层推上嵌入式

Figure AI 的 Helix 是这套架构里最极端的一份答卷。

| | System 2 | System 1 |
|---|---|---|
| 规模 | 7B VLM（开源权重、互联网规模预训练） | **80M** 交叉注意力编解码 Transformer |
| 频率 | 7–9 Hz | **200 Hz** |
| 职责 | 场景理解、语义泛化、把指令蒸馏成潜在向量 | 精确连续动作 |
| 部署 | 高算力、高显存 GPU | 低延迟、高能效专用 GPU |

**注意 S1 只有 8000 万参数。** 相对 S2 小了两个数量级。这个反差是整份设计里最有信息量的地方：**高频控制需要的能力，和学习语言、理解场景所需的能力，完全不在一个量级上。** S1 的视觉骨干甚至是纯仿真预训练初始化的。

Helix 覆盖人形机器人上半身 **35 个自由度**——手腕、手指、躯干、头部全在一起，全部在嵌入式 GPU 上跑，没有云端推理。这一点对落地是决定性的：工厂和家庭都不会给机器人配一条低延迟专线。

另外两个「第一次」：

- **第一个能同时操作两台机器人的 VLA。** 两台用相同权重的机器人，无需训练、无需分配角色，靠自然语言协作完成长时程放置任务。
- **Helix 02 把控制扩展到全身。** 把行走、操作、平衡整合进单一连续系统——演示里它自主完成了整个厨房的洗碗机装卸，**四分钟不间断，没有 reset，没有人工干预。**

数据量上有个反直觉的数字：**Helix 大约只用了 500 小时遥操作数据。** 对比 GR00T N1 的两万小时以上第一视角人类视频加合成数据，这个数字少得惊人。它的补偿机制是让 S2 用语言给数据自动打标，把数据的利用率拉高——**数据少，但每条被榨得更干。**

## 三、GR00T N1：同样的分层，相反的耦合

英伟达的 GR00T N1 选了一模一样的两层结构，但在一个关键点上做了相反的选择。

**Helix 是松耦合（分频并行），GR00T N1 是端到端联合训练。**

具体规格：

- **S2**：基于 NVIDIA Eagle-2 的 VLM，SmolLM 1.7B 语言骨干 + SigLIP-2 图像编码器，约 10 Hz
- **S1**：Diffusion Transformer，**120 Hz**，用扩散去噪生成平滑动作
- 公开 checkpoint **GR00T-N1-2B 总共约 22 亿参数**（其中 VLM 13.4 亿），在 L40 上采样 16 个动作耗时 **63.9 毫秒**
- 训练消耗约 **5 万 H100 GPU 小时**，数据混了真机轨迹、人类视频和 Isaac 仿真合成数据

**「联合训练」这个词值得展开。** Helix 的两个系统各自训练、接口固定；GR00T N1 让 S2 和 S1 在 post-training 阶段一起优化。代价是训练更复杂、更容易互相干扰；收益是接口本身也被优化了——S2 会学着输出「对 S1 更好用」的向量，而不是「对人类看起来更合理」的向量。

这条路上的迭代速度也说明问题：N1.5 更新 VLM 到 Eagle 2.5 并加了 FLARE 损失从人类视频里学，**真机 GR-1 上的指令跟随率从 46.6% 提到 93.3%**；N1.6 换上 Cosmos-Reason-2B 变体、DiT 层数翻倍到 32 层。**一版之内指令跟随率翻倍，说明这个位置原本就是个明显的短板。**

还有个战略层面的细节：GR00T N1 是**开源**的，被 1X、Agility、Apptronik、Boston Dynamics、Figure、宇树、小鹏机器人等采用。这跟 Figure 走闭源自研、Physical Intelligence 走「卖智能层」的路子形成了三种不同的商业假设。谁的假设对，现在还没答案。

## 四、π0.5：不切分的那种做法

Physical Intelligence 的 π0.5 给了第三种答案：**不硬切。**

它用统一 Transformer，同时输出语义子任务文本和动作 token，靠不同的输出头区分模态，权重全程共享。动作生成走流匹配，50 Hz。

和硬切分的对比很清晰：

| | π0 / π0.5 | Helix | GR00T N1 |
|---|---|---|---|
| 语义层频率 | 内嵌（思维链式） | 7–9 Hz | ~10 Hz |
| 动作层频率 | 50 Hz | **200 Hz** | 120 Hz |
| 耦合方式 | 单塔 + 双层推理 | 分频并行（松） | 端到端联合训练（紧） |
| 参数量 | ~3.3B | 7B + 80M | 2.2B（公开版） |
| 训练数据侧重 | 多样环境 + 网页数据 + 跨本体 | ~500 小时遥操作 | 2 万+ 小时第一视角人类视频 + 合成 |

**统一架构的好处是省掉了「翻译」环节**：S2 不用把理解压缩成一个向量再交给 S1，语义和动作在同一组权重里流动。代价是推理时得多跑几步，动作频率因此落在 50 Hz 这一档，低于两个硬分层方案。

谁更对？现在没人知道。有个现实的观察：**π 系列是在轮式移动操作平台上做的，没有双腿。** 腿是这套架构里最吃频率的部分——平衡补偿基本得跑在几百赫兹。所以 π0.5 的 50 Hz 在轮式平台上够用，不代表在人形腿上够用。**跨平台比较性能数字其实意义不大，因为平台面对的挑战本身不同。**

## 五、Google 的另一种切法

Google DeepMind 的分层切在更上面一层：Gemini Robotics 1.0 分成两个模型——**Gemini Robotics-ER 负责具身推理**（物体检测、轨迹预测、3D 空间理解），**Gemini Robotics 负责实际控制**。

这跟「S2 规划、S1 执行」的分法区别在哪？**它把「想」和「动」之间的接口做成了可解释、可外挂的模块。** 具身推理单独成一个模型，意味着你可以换掉它、单独评估它、让它接别的控制器。

这个设计有个直接好处：**100 个 demo 就能学会新的短任务**，并且支持跨本体迁移。数据效率的来源是「推理层已经会推理了」，新任务只需要教会动作层一段短映射。

## 六、π0.5 自己承认的三种失效

现在说最有价值的部分。π0.5 的论文列了几条持续的失效模式，**每一条指向的都是同一个缺失：世界状态。**

1. **没有持久空间地图。** 它看不到身后，物体被挪走之后也记不住位置。需要「记得我把东西放哪了」的任务会失败。
2. **高层子任务预测器会被显著但无关的物体带跑。** 一个已经处理完、但视觉上很抢眼的物品，会重新吸引它的注意力，让它反复往那儿凑。
3. **没有失败恢复机制。** 抓取失败或者掉落了，模型不会检测到失败并重新规划。

第二条的成因写得很明白：**它没有显式的世界状态表示**，只能从每个时间步的原始视觉观测里去推断当前状态，而不是查一份维护中的任务进度记录。

**这就是[第一篇](/agent/posts/2026-09-18-embodied-driving-first-ai/)里说的「世界模型」要补的位置。** 世界模型不只是「预测下一帧」这么一个炫技功能，它提供的是一份**可查询的状态**——物体在哪、任务做到第几步、上个动作有没有生效。缺了它，模型每一步都在重新猜这个世界长什么样。

也正因如此，α（世界模型）和 β（VLA）的融合（第二篇讲的 WAM 方向）不是路线选择问题，是**能力互补问题**。

## 七、对驾驶这边的一句话

如果你把这个架构映射回自动驾驶，会发现一件有意思的事：**AD 的双系统早就存在了，只是没人这么叫。**

规划模块跑 10 Hz 量级、控制模块跑 100 Hz 量级，中间靠轨迹做接口——这和 Helix 的「S2 出向量、S1 出动作」是同一个模式的两个实例。区别在于 AD 的中间接口是**人定义的、可解释的**（一条轨迹），而机器人的是**学出来的、不可解释的**（一个潜在向量）。

这个区别决定了两个领域各自最头疼的问题：AD 头疼长尾场景下规划器给不出合理轨迹，机器人头疼那个潜在向量里到底有什么、出问题时看不懂。

**顺带说一句，这正好是第一篇里「模块化 vs 端到端」那条线的延续——** AD 用可解释接口换可靠性，机器人用学习接口换泛化。而两边都在往中间靠。

[DINOv3 系列](/blog/series/dinov3-e2e-ad/)里讲的「冻结编码器 + 轻量适配器」，本质上是 AD 语境下对同一个频率矛盾的另一种回答：**把最贵的那个模块固定住、让它不参与高频更新。** 思路和 Helix 把 80M 小模型放在 200 Hz 位置上是同源的。

下一篇回到数据这一侧：既然分层已经把「怎么想」的问题缓解了，那「拿什么练」就是剩下的那堵墙。
